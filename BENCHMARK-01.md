# BENCHMARK-01 — downstream utility

**Status:** design + pre-registration. **Not run.** No task set, no calls, no spend yet.
This document exists so that the question in §1 is answered by a measurement that was fixed before it
was taken.

---

## 1. The question

> Does an agent working from this engine's context state complete real tasks more often, or more
> cheaply, than the same agent working from a summary — or from the whole source?

Everything measured so far is upstream of that question. H1–H8 ask whether the pack *contains* the
evidence: quotes resolve, facts appear, attribution matches, omissions are listed. A pack can pass
every one of those gates and still be useless, because a task may need a relationship no finding
records, or because reading 3,000 tokens of JSON is harder than reading the 800-word source it
replaced.

The benchmark is the only experiment in this project that can fail in the direction that matters.

**Falsified if:** the pack condition's task success is materially worse than the full-source condition,
or its cost per solved task is not materially lower. Both are needed: "cheaper but worse" and "better
but not cheaper" are different products, and neither is the one being claimed.

## 2. Conditions

Five conditions, same task set, same answering model, same harness.

| id | Context given to the agent | What it tests |
| --- | --- | --- |
| **C1 pack** | the contradiction-bearing medium pack (~3k tokens) plus its source index | the product claim |
| **C2 summary** | a summary generated by the **same model** with the **same token budget** as C1 | the thing this engine exists to replace |
| **C3 source** | the complete subject tree, inline | the ceiling: full information, full cost |
| **C4 grep** | the tree on disk plus file-read/search tools, no pre-built context | what a competent agent does today |
| **C5 retrieval** | (deferred) on-demand queries against the snapshot with citations | the reframed product in §9 |

C1 and C2 are deliberately token-matched. If the pack wins on a larger budget, the win is uninformative.
C3 and C4 are not budget-matched, because their cost is the thing under test.

The summary in C2 must be produced by the same model from the same source, with the same output-token
ceiling, and stored as an artifact. A summary written by a human, or by a stronger model, makes the
comparison a test of summariser quality rather than of representation.

## 3. Task set

**Subject:** one real public repository of 40–120 files, with a test suite. Not the 11-file fixture:
that subject is smaller than the pack, so it cannot show an economic result at all.

**Twelve tasks**, each with a mechanical check, in three families:

| Family | Example | Check |
| --- | --- | --- |
| Locate | "Which module decides expiry, and what calls it?" | expected path(s) + relationship, matched exactly |
| Change | "Make the configured retention value take effect in the expiry path." | repository test suite, or a task-specific test |
| Explain | "Why is retention fixed rather than sliding, and what was rejected?" | required claims + required citation |

Task sources, in order of preference:

1. **The repository's own bug-fix commits and issues** — written by strangers, which is the point.
2. Existing tests that fail when a specific line is reverted.
3. Hand-written only where 1 and 2 give nothing, and marked as such in the artifact.

**Contamination control.** Tasks must not be answerable from the issue text alone, and the answering
model must not be given the issue. Where a task comes from a public fix, record the commit and check
that the answer is not quoted in the task statement.

**Difficulty control.** Each task is dry-run under C3 (full source). A task that C3 solves trivially and
C2 also solves trivially measures nothing; a task C3 cannot solve measures the model, not the context.
Tasks outside `0.2 ≤ C3 pass rate ≤ 0.9` over the pilot repeats are replaced **before** C1 is scored,
and the replacement is recorded.

## 4. Metrics

Reported per condition, per task, with raw counts:

| Metric | Definition |
| --- | --- |
| **Task success** | the task's check passes, judged by the harness, not by a model |
| **Cost per solved task** | (construction cost ÷ tasks) + answering cost, summed over solved tasks only |
| **Construction cost** | scan + verify + pack (C1), summary call (C2), zero (C3/C4) — amortised over the task set |
| **Answering tokens** | provider-reported input + output per task |
| **Wall time** | per task, and total including construction |
| **Context tokens delivered** | what the condition actually put in front of the model |
| **Failure attribution** | missing context / wrong context / reasoning error / tool misuse, assigned by the harness where mechanical, by a blinded rater otherwise |

Two cost figures are reported for C1: **steady-state** (pack already exists) and **cold** (construction
included). Reporting only steady-state would hide the engine's main expense.

## 5. Equivalence controls

- Same answering model, temperature 0, same output cap, same system prompt except the context block.
- C1 and C2 receive the same token budget (calibrated, see §6), packed differently.
- Same task wording, same order, same retry policy: **none**. A failed call is a failed call.
- Scoring is executable. Where a rater is unavoidable, they see the answer without the condition label.
- Costs use provider-reported figures; the catalogue product is recorded separately as in every other
  run here.

## 6. Token budget and estimator

`poc/calibrate.js` measured the estimator against provider-reported usage on 2026-11-20: **3.47 and
3.82 chars/token**, so `ceil(chars/4)` understated the scan prompt by **13.2%** and the QA prompt by
4.5% (mean 3.64). Two consequences, both pre-registered here:

1. Budget gating in this benchmark uses **3.5 chars/token** (the pessimistic figure), not 4.
2. Every report states pack size **twice**: the artifact's `ceil(chars/4)` estimate and the calibrated
   figure. A condition that "fits 4,000 tokens" but bills 4,400 is not a 4,000-token condition.

## 7. Pre-registered verdict rule

Fixed before the run; no threshold moves afterwards.

| # | Requirement | Kind |
| --- | --- | --- |
| **B1** | C1 task success is not worse than C3 by more than **1 of 12** tasks | non-inferiority |
| **B2** | C1 cost per solved task is **≤ 70%** of C3's | economics |
| **B3** | C1 task success is **≥** C2's on at least **8 of 12** tasks | beats the summary |
| **B4** | every C1 answer that cites a source cites one present in the pack index | integrity |
| **B5** | construction cost, answering cost and totals are provider-reported and within the authorised cap | reporting |

"Supported" requires **B1–B4**. B1 alone would bless a cheap-but-worse system; B2 alone would bless a
system that saves money by failing. B3 is the claim that matters against the status quo.

**Repeats.** Three per condition (60 tasks × 3 ≈ 180 answering calls) to report variance rather than a
single sample — the two live scans in this folder already disagreed about which gate failed, and a
benchmark with n=1 per cell would inherit that.

**No significance claims at n=12.** Report per-task paired outcomes and counts. If C1 and C3 differ on
one task, that is one task, not a trend.

## 8. Spend and stopping

| Item | Calls | Estimate |
| --- | ---: | ---: |
| Construction: scan + QA + delta on the subject | 3–6 | ~$0.004 |
| C1 answering | 36 | ~$0.007 |
| C2 summary + answering | 1 + 36 | ~$0.008 |
| C3 answering (full source, large prompts) | 36 | ~$0.05 |
| C4 answering (tool turns, several calls per task) | ~100 | ~$0.03 |
| **Total** | ~215 | **≈ $0.10** |

Rough, and deliberately conservative. Each condition runs under its own `--run-id` through the spend
guard; a retry needs a new authorisation and is recorded. Stop conditions, in order:

1. citation failure above 20% in construction → stop, the pack is not fit to test;
2. spend reaches the authorised cap → stop and report the partial matrix;
3. C3 cannot solve more than 2 of 12 tasks → the task set is too hard; fix tasks, do not score C1;
4. the resolved model is not the registered model family → stop, record the alias drift.

## 9. Where this leaves the product

The pack is one delivery mechanism. If C1 wins, the next question is whether **C5 retrieval** — asking
the snapshot for the slice a task needs, with citations — beats a fixed pack at the same cost, because
a pack has to guess what the agent will need and the snapshot does not. This benchmark is designed so
that adding C5 requires no changes to the other four conditions.

## 10. What this will not establish

- **Generalisation.** One repository, one model family, twelve tasks.
- **Long-horizon sessions.** Compaction happens once; repeated compaction drift is unmeasured.
- **Multi-partition behaviour**, unless the chosen subject exceeds the 400k budget (it will not).
- **Causation for cost.** A cheaper C1 may reflect shorter context, not better context; failure
  attribution is reported to keep that distinction visible.
- **That the pack is safe to rely on.** Integrity gates are measured separately and remain the
  precondition, not the result.
